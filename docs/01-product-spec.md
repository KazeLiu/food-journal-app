# 01 产品规格

## 1. 产品目标与范围

用户说“中午吃了一碗牛肉面”，APP 理解已发生的饮食，估算大概热量和营养，保存并简短回应；偶尔称重也用同样方式记录。不必称食物，不必填写健康问卷，不因漏记被指责。

功能完整不等于首页堆满功能：聊天负责记录和交流，月历负责回顾，食品资料和记忆管理放在“我的”。分享对话末尾的精简要求不作为删除此前逐项选定设计的依据。

## 2. 记录意图与分组

| 输入 | 行为 |
| --- | --- |
| 中午吃了一碗牛肉面 | 新建午餐，按常见份量估算 |
| 晚上吃了米饭、鸡翅和青菜 | 一餐内保存三个食物项 |
| 刚才还喝了一杯酸奶 | 结合上下文追加到原餐，不重复整餐 |
| 刚才那碗只吃一半 | 修改原食物和营养，不新增半碗 |
| 牛肉面一般多少热量 | 只回答，不记账 |
| 晚上准备吃面 / 这是菜单 | 讨论计划，不记成已吃 |
| 又吃了一份面 | 明确新增，不按同名去重 |
| 短时间重复说“牛肉面一碗” | 明显疑似重复时询问是不是同一顿 |
| 今天 132 斤，中午吃了面 | 独立处理体重和午餐，分别反馈 |

一条 `meal` 是一次饮食事件，内部一个或多个 `food_item`。餐别 `breakfast / lunch / dinner / other`，显示早餐 / 午餐 / 晚餐 / 加餐或其他。同日同餐别可有多条事件，不强行合并不同时刻吃的两碗面。

删除最后一个食物时一起标记删除空餐。餐与日合计从有效食物计算，不另存容易过期的总数。

## 3. 时间与上下文

- 入队固定参考日期、时间和 UTC 偏移，跨午夜返回、重试或换兜底仍沿用原时间。
- 用户明确给出的日期优先，否则使用日历选定日期，未选日期才默认发送当天；“前几天”等歧义直接问，不随意归今天。
- 日历定向进入聊天携带日期 / 记录 ID，输入时显示可退出上下文条，发送后在消息中保留可点击标记。整天分析使用所选日完整合计，历史消息标注各自日期；用户明确说“今天”仍优先。单纯浏览日历不改变聊天默认日期。
- 明确餐别优先于时钟。否则 AI 结合描述与时间；参考时段 05:00–10:59 早餐、11:00–14:59 午餐、17:00–21:59 晚餐，其余其他，不用时段推翻用户。
- 今天新增记录没有说时间时，默认取发送时刻；识图等待、兜底和重试都不改变该时间。“两个小时前”按参考时间计算。
- “昨天上午”“前天下午”“中午吃了面”只保留用户说出的时段，不补造几点几分。历史日期未给时段或具体时刻时只记日期，卡片不显示“未注明时刻”。
- 手动新增饮食和体重默认打开表单时的当前时间，可调整或清空；编辑既有记录保留原时间。
- 发生时间与录入时间分开。换时区不挪历史 `local_date`。
- 定向操作完成、用户退出或切回今天后清除历史上下文；排队消息保留各自发送时的上下文。

### 按日期提供上下文（D09，已明确需求，待开发）

- 未引用特定日期时，主对话默认提供原消息发送当天的全部有效业务记录：各次饮食、每项食物及已知营养、全部体重；运动功能实现后同时包含各次运动及已知时长、消耗。
- 明确引用其他日期或从日历定向进入时，按该日期提供数据；明确说“今天”仍优先。比较多个日期时只补充涉及日期，例如“和昨天比，我今天吃得多了还是少了”需要今天和昨天。
- 不再默认混入跨日的最近食物、体重和聊天来代替按日数据。业务事实从当前有效记录读取，不累加旧聊天中的估算或已被纠正的值。
- “全部数据”指范围内完整业务记录，而非整库、操作日志或全部历史图片。当天聊天原文的携带范围、长期记忆筛选和超出上下文预算时的处理仍需细化，不将现有条数截断后的快照称为“当天全部”。

普通文字请求推荐一次完成；需要范围外数据时沿用受限本地查询，再请求模型生成答案，不为每条消息单独增加意图识别调用。具体调用建议见 04 第 6 节和 09 的 D09。

## 4. 营养估算

各食物保存 `calories_kcal / protein_g / fat_g / carbs_g`，每项允许未知。热量显示整数 kcal，营养素一般一位小数；标签原数值随来源资料保存。不为凑热量强行改动用户提供的营养素。

### 来源优先级

1. 用户针对本次食用量明确提供的数值。
2. 当前清晰、匹配产品的包装营养标签。
3. 已确认、品牌 / 口味 / 规格匹配的本地食品资料。
4. AI 根据食物、自然份量和做法粗估。

同一食物可有用户热量、标签蛋白质、AI 脂肪等不同来源。估算依据当时保存，详情按需展开，不能事后编造当时依据。AI 若给出有意义的热量区间，随依据保存 lower_kcal / upper_kcal；主展示仍为“约 N kcal”，区间不冒充测量精度。

标签须区分每 100g、100ml、每份、每包装，换算实际食用量。1 kcal = 4.184 kJ；不能将每 100ml 直接当整瓶，缺密度时不直接将 g 与 ml 互换。看不清数字就说明、询问或采用明确标注的普通估算，不能猜成标签数据。

没有克数时按碗、盘、盒、少量估算。只有不知道主要食物、日期或对象等关键内容才追问。用户说“随便估一下”且仍有可用信息时粗估并保存，简短标注不确定性；完全不知食物是什么时不编造。

### 空值与补算

- 未知是 NULL，不是 0，真实零值有效。手动记录只要求名称，份量和营养可空。
- 下次前台正常 AI 使用成功、用户队列处理完后，补充所有日期缺失字段；只填仍为空且版本匹配的值，不重估已有数值。
- 仅缺蛋白质等字段、已有热量时也可补，已有热量保留。无法估算继续未知并保存原因。
- 不在后台定时探活，不因补算成功再次触发自身。

## 5. 图片与模型

D10 已确认：所有模型首次失败后都在同一模型重试一次；主模型两次失败才切换已配置的备用，备用最多也尝试两次，任一次成功即停止。此规则覆盖文字、识图、查询后总结、补算、食品资料识图和能力检查，具体边界与调用上限见 04 第 3 节，当前实现与验收范围见 10。

单条最多 3 图，可以是包装正面、营养表、实际份量；同盘不同角度不能变多餐。入口只有拍照 / 相册，AI 判断类型，发送前保守压缩保留小字清晰度。

聊天和食品表单分开显示上传与等待：先按实际请求字节显示本机发送百分比，发完后才开始两分钟减速的识别预估。前者不是服务端收件确认，后者不是模型真实完成比例；不改变现有超时与重试上限。

D03 采用两阶段：图片主备产生可保存的识别 / 标签摘要，文字主备结合上下文和本地资料处理记录。均只用 Responses。文字阶段失败只重试文字，不要求重传。按用户确认保留 APP 私有压缩预览，发送后可看小图、点击看大图；删除聊天或清空数据时清理，不进入备份。识图主备均失败仍保留预览，提供重试、重选和手动入口，详见 04、05。

仅发清楚食物照默认记录图中这一份；菜单、非食物或明确咨询不自动记录。追问后将摘要和回答用于原事项，不把回答再记成一顿。相册原图始终不删。

## 6. 纠正、撤销与部分成功

- 唯一对象直接改；指代不清给简短候选。真实 ID / 版本定位，不按名称批量覆盖。
- 食物或份量改变时，同步更新受影响营养与依据；明确只改某字段不覆盖其他字段；整体换成另一种食品不能沿用旧营养。
- D01 保留直接编辑，AI 修改为主，详情更多可本地编辑。改名称 / 份量清空受影响数值供确认或补算；只改日期、时间、餐别不清营养。
- D02 支持长按引用，不增加右滑。引用帮助定位，不自动授权修改；源消息删除后可保留必要摘要但不能恢复记录。
- 新增、修改、删除有简易操作历史，支持具体一项撤销，不是删上一条消息，也不自动重做后续操作。
- 一条消息的独立事项分别提交。一项失败或待澄清，其他明确项可保存；同一餐及其食物为一个完整保存单位。
- 重试只处理未完成项；成功项即使后来被删除，也不能靠原消息重试复活。
- 删除聊天不删饮食、体重、已确认资料、记忆和操作去重凭据。

## 7. 体重

斤 / 公斤，1 斤 = 500 克，统一值整数克，保留原输入值与单位。未写单位用偏好，默认斤，回执明确单位。

同日每次测量独立保存，不取均值、不覆盖。“刚才记错”改原条，“现在又称了”新增。最近一次按已知测量时间取最新；未知时刻单列按录入顺序。切换单位只换算显示，不重写原值。

日历与历史页提供查看、删除、纠正和快捷录入。不主动比较涨跌；用户问“比上次轻多少”才比较真实记录，不做趋势或预测。

## 8. 食品资料与长期偏好

常用餐食保存名称 / 别名、习惯份量、营养估算和依据。包装食品保存品牌、产品、口味、规格、基准、营养原值和来源。AI 可建议，用户同意才保存；拒绝不影响本餐。

AI 拍照填表和聊天资料建议可联想常用简称、俗称，例如零度可口可乐的“零度可乐、零度、无糖可乐”。别名允许人工修改，不伪造不同品牌或口味；同一泛称匹配多款食品时仍需澄清。

添加食品资料的表单右上角提供 AI 拍照识别：可拍同一食品最多3张照片，开始识别后由图片模型综合填入名称、规格、营养和备注，用户核对修改并点击保存才入库，不创建饮食或聊天。识别时用不可被遮罩或返回关闭的模态框显示预估进度，可明确停止；完成后仍在表单，提示需要手动保存。包装标签只读取可见字段，配料、过敏原等写入可编辑备注，普通餐食明确标为 AI 估算。食品照片暂存在私有表单草稿，保存或放弃后清理，不进备份；相机导致进程重建时回到该表单。

同名份量变化要换算；口味 / 规格不同时不随便套用。清晰新标签与旧资料不同，本餐可用新数据，长期更新另行确认；历史不被资料更新重算。“我的”可查看、编辑、删除，来源只在详情小标签提示。

自动匹配同时查看名称、别名和品牌，精确名称 / 别名优先，品牌仅作为候选线索，不把同品牌所有产品视为相同食品。纠正名称或要求重新计算时先核对已保存资料，按明确食用量用库中原值换算。后续要求保存刚拍过的标签或补包装规格时，可继续引用该图片已保存的识别摘要；建议仍需确认后才入库。

长期偏好、交流风格经确认后保存，临时情绪或单次饮食不永久化。用户可查看、改、删；同一拒绝建议不反复出现。主动明确要求“记住我不喝牛奶”即授权该项保存，可撤销。

记录和聊天历史不等于长期记忆授权。只向服务发送当前任务需要的已确认资料，不上传全库。

## 9. 展示与反馈

首页固定显示已记录餐数、热量、待估算信息和三个快捷入口，下方聊天独立滚动；完整营养在卡片展开和日历详情。

餐数按当天有记录的早餐 / 午餐 / 晚餐餐别去重，其他事件另计次数。营养字段独立求和和统计缺失，无记录不显示“全天摄入 0”，部分值不冒充完整合计。

回复简短、友好，偶尔自然关怀，不评价食物好坏、不催控制。生成气泡处于未完成状态，实际成功文字和卡片由客户端提交结果生成，多项操作分别反馈成功、失败、待确认。

## 10. 数据与交付

SQLite 保存聊天、记录、操作历史、食品资料、授权记忆和非敏感设置；Key 用安全存储。CSV 便于查看，完整备份用于恢复，支持可选密码，不含 Key、AI 连接配置和原图。整库替换前预览并保留最近一份安全副本。

当前源码与 APK 交付状态见 10。真实服务、图片识别表现和设备交互按 06 由用户验收。

## 11. 运动记录扩展（设计中）

### 使用方式与已明确需求

用户可以一次讲述一天的饮食和运动，不必分别切换入口。例如：

> 我上午吃了60克卤牛肉和500毫升牛奶，中午吃了300克鸡胸肉，晚上吃了一个100克的杂粮饭，游了个泳，然后晚上吃了五把爆米花。

识别内容应保留为：

- 上午饮食：卤牛肉 60 克、牛奶 500 毫升。
- 午餐：鸡胸肉 300 克。
- 晚餐：杂粮饭 100 克。
- 运动：游泳，用户没有提供时长、距离、强度或消耗。
- 晚间加餐：爆米花 5 把，保留自然份量，不并入之前的杂粮饭。

饮食仍按现有规则处理餐别、时间、营养与来源；运动是独立记录，不作为食物项或餐别。沿用“AI伙伴、我的记录、我的”三个入口，运动内容在“我的记录”中查看。

### 推荐方案，待用户确认

- 只说“游了个泳”时先保存运动名称，时长与消耗留空，AI 可顺带询问时长；不因运动信息不足阻塞明确的饮食项。
- 补充“半小时”时更新已定位的游泳记录，不重复新增；“又游了半小时”表示新的运动事件。对象不明确时先澄清。
- 允许记录运动消耗，用户明确提供的数值优先；AI 估算标明来源和依据，不编造时长、距离、强度或体重。是否估算、所需信息和计算口径按 09 确认后确定。
- 饮食摄入与运动消耗分别展示，不把运动保存为负数食物，不自动将两者之差命名为“热量缺口”。
- 建议与现有记录能力对齐：聊天纠正、直接编辑、删除、逐项撤销、历史查询、离线手动记录及数据导出恢复。

“准备去游泳”和“游泳一般消耗多少”属于计划或咨询，不新增已完成运动。建议此次扩展不增加运动计划、计时器、设备同步、热量目标或新的健康问卷。
