# 01 产品规格

## 1. 产品目标

用户只需发送“今天中午吃了一碗牛肉面”，APP 就能理解已发生的饮食、估算热量、保存记录，并给出简短回执。偶尔记录体重也用同样轻松的方式完成。

这是记录工具，不负责监督饮食。热量可以近似，记录归属、修改对象和保存结果必须可靠。

### 成功标准

- 明确的饮食描述不用填写复杂表单即可记录。
- 份量不详细时使用常见份量，不反复索要克数。
- 能把“只吃了一半”等纠正应用到原食物，而不是新增一份。
- AI 不可用时不妨碍本地查看、新增、编辑、删除和备份。
- 日历能看清当天已记录的饮食、已知热量和全部体重记录。
- 不将漏记食物或待估算热量算成零，不把已记录的合计说成全天实际摄入。

## 2. 范围与需求编号

| 编号 | V1 要求 |
| --- | --- |
| R01 | 三个底部页面；自然聊天；历史持续保留；消息前台串行排队 |
| R02 | 自然语言记录一个或多个食物，保存日期、餐别、份量描述和估算热量 |
| R03 | 明确区分进食事实、咨询、计划、聊天、纠正和删除 |
| R04 | 拍照 / 相册，单消息最多 3 图，图文混合，成功处理后删除临时图 |
| R05 | 斤 / 公斤体重记录、单位偏好、一天多次、历史查看与纠正 |
| R06 | 日历日期标记、分餐展示、已知热量合计与待估算提示 |
| R07 | 饮食 / 体重聊天纠正、直接编辑、删除和离线手动新增 |
| R08 | 仅 Responses API；Base URL / Key、拉取模型列表、手输 ID、文字与图片分别主备、连接检查 |
| R09 | 主备均失败时提示失败、保留文字、允许手动重试与手动记录 |
| R10 | 手动热量允许空；下次 AI 成功后自动估算空值 |
| R11 | 本地事务、操作去重、修改冲突处理；成功回执与保存结果一致 |
| R12 | 删除聊天不删除记录；记录详情和统计以当前数据为准 |
| R13 | 本地备份、整库恢复、清除数据；Key 安全保存 |
| R14 | 轻松、温柔、易读、单手操作；不用目标或评价制造压力 |

### 不在 V1 范围

账户、登录、自有服务端、在线数据库、云同步、多设备同步、社交、条形码、商品或个人食品营养库、精细营养素、热量目标和剩余额度、体重趋势或预测、BMI、减肥计划、提醒、打卡奖励、语音输入、常驻虚拟形象、复杂动画、复杂聊天引用、向量库或长期记忆管理、多服务商调度。

固定的文字 / 图片主备链属于本版范围；不扩展为多模型路由、自动排行榜、后台探活或无限重试。

## 3. 饮食记录语义

### 3.1 意图规则

| 用户输入 | 处理 |
| --- | --- |
| 中午吃了一碗牛肉面 | 新增午餐记录并估算 |
| 晚上吃了两碗米饭、一份番茄炒蛋和一点青菜 | 同一餐内保存三个食物项 |
| 刚吃了一个苹果 | 新增饮食；按上下文决定餐别，不明确时归“其他” |
| 一碗牛肉面多少热量 | 只回答，不保存饮食 |
| 晚上准备吃牛肉面 | 只聊天，不提前记录 |
| 这是菜单，帮我看看选什么 | 只讨论，不把菜单内容记为已进食 |
| 昨天中午那碗面忘记记了 | 补到昨天午餐 |
| 刚刚那个苹果其实只吃了半个 | 定位原食物，同时更新份量、热量和当前描述 |
| 刚才还喝了一杯奶茶 | 表示额外摄入，新增食物；上下文明确同一餐时加入该餐 |
| 把昨天午饭里的米饭删掉 | 明确定位后删除该食物，不删除其他食物 |

一条消息可以同时产生饮食和体重操作，作为一次本地事务保存。普通聊天不得为了凑结构而产生空饮食记录。

### 3.2 餐与食物

- 一次饮食记录称为一条 `meal`，其中有一个或多个 `food_item`。
- 餐别仅有早餐、午餐、晚餐、其他，内部值为 `breakfast / lunch / dinner / other`。
- 同一天同餐别可以有多条饮食，日历放在同一个餐别分组下，不强行合并不同摄入事件。
- “这顿还吃了……”且指向明确时，在现有餐里添加食物。
- 每个食物分别保存名称、份量文字和热量，餐热量、日热量都由食物项计算，不另存容易过期的总数。
- 删除最后一个食物时一并删除空餐；删除整餐时删除其食物，不留下没有内容的日历标记。

### 3.3 估算与澄清

- 没有克数时按常见份量；“一点”“半碗”等可以估算。
- 明确给出食物和实际热量时使用用户给出的热量，标记来源为用户填写。
- 对影响较大的假设只用一句话说明，例如“按普通餐馆一碗估算”。
- 缺少份量通常不追问；不知道吃的是什么、是否已吃、应修改哪条记录时可以询问。
- 同一条消息有必须澄清的关键内容时，先询问，暂不部分保存其中的其他操作。下一条回复补充后，再整体保存，避免用户补充时重复录入。
- 照片无法识别就直说，不编造菜名或热量。
- 单独发送清楚的食物照片，默认是在记录这份饮食，按图中展示份量估算；可以说明“按图中这份估算”，不声称看到了用户实际吃完的过程。菜单、非食物或文字明确表示咨询时不自动记录。
- 同组多图按一条消息共同理解；同一盘食物的不同角度不能重复计数。无法判断是重复照片还是不同份时简短询问。

文档中的热量数字用于演示交互；开发时不得把这些数字实现成固定食物数据库。

## 4. 时间规则

- 发送时固定本轮参考时间，包含手机本地日期、时间和 UTC 偏移；主备请求使用同一参考时间。
- 没有说日期时默认发送当天。已排队、跨午夜返回或第二天重试，都不将原输入改成新一天。
- “昨天”“前天”等相对日期按本轮参考时间理解；明确日期优先。
- 明确餐别优先于发送时间。“晚上补记中午那碗面”属于午餐。
- 没有餐别、上下文也不能确定时，可按本地时间估计：05:00–10:59 早餐、11:00–14:59 午餐、17:00–21:59 晚餐，其余为其他。用户明确说零食、加餐、饮料单独喝时归其他。
- “中午吃了……”只知道日期与餐别，不伪造实际进食的具体时刻；详情标为“时间未注明”。
- “刚刚吃了……”或“今天 132 斤”未另指定时间时，以消息发送时间记录。
- `created_at_ms` 始终保存真正录入时间，不能与发生时间混用。
- 改日期时同时刷新旧日和新日的汇总；手机以后换时区，不自动挪动历史记录日期。

## 5. 纠正、直接编辑和删除

### 聊天纠正

1. 依据当前数据库和近期对话定位，不只依据旧聊天回执。
2. 唯一匹配时修改；多条苹果、面条或体重都可能匹配时询问，或展示简短候选供点击。
3. 更新使用明确 ID 和版本，禁止按名称批量修改。
4. 已删除或用户刚改过的记录，不靠陈旧 AI 结果恢复或覆盖。含图请求涉及既有记录修改 / 删除时，额外展示目标与变更供用户确认；纯文字唯一目标纠正保持直接保存。

### 直接编辑

- 饮食可改名称、份量、热量、日期、时间、餐别；体重可改数值、单位、日期与时间。
- 本地完成，不调用 AI，不依赖联网。
- 改食物名称或份量时清空热量输入框，并提示“请确认热量；也可以留空，稍后估算”。用户可填写数值或直接保留空值。
- 只改日期、时间、餐别、备注时保留原热量。
- 用户实际填写或修改的热量标记为 `user`；未改热量时保留其来源。空值标记为 `unknown`，以后由自动估算处理。
- 直接改错不会改写过去的聊天原文。关联记录卡片读取当前值；记录被删除时卡片显示“记录已删除”。

### 删除

- 详情中的删除需确认对象；明确的聊天删除指令在唯一匹配时可直接执行。
- 删除聊天只删除聊天及其 APP 临时附件，不删除饮食、体重或用于去重的已提交操作。
- 删除记录后不自动回放原消息；已有消息的重试也不能把已删除记录重新生成。

## 6. 体重规则

- 支持“今天 132 斤”“今天体重 66 公斤”。
- 单位枚举仅 `jin / kg`；1 斤 = 0.5 公斤 = 500 克，统一计算值用整数克。
- 保存原始输入数值和单位，切换显示单位不重写历史原始值。
- 未写单位时使用“我的”中的单位偏好，默认斤；回执明确显示最终单位。
- 一天多次记录全部保留；日历按已知时间排序，没有具体时间的另行标注。
- “刚才其实是 131 斤”修改对应记录；单独再发“现在 131 斤”表示新测量，不按同日自动覆盖。
- 只校验合法正数、受支持单位和有效日期；不依据 BMI 或体型评价输入。

## 7. 手动新增与空热量

- 日历和聊天失败消息均可打开手动新增。
- 饮食至少填写食物名称；日期、餐别使用当前场景默认值，份量和热量可空。
- 来源消息只有文字时预填原描述，不能在 AI 失败后用简单关键词偷偷把体重或热量猜入库。
- 体重手动新增需要数值，单位使用偏好。
- 热量空值保存为 SQL `NULL`；真实的 0 kcal 可以保存为整数 0，二者显示与统计不同。
- 空值显示“待估算”，缺少足够描述而暂时算不出时保留原因。
- 下一次前台正常 AI 请求成功后自动尝试补充所有历史日期的空热量。主备仍失败就保留空值，详见 05。

## 8. 首页与日历统计口径

- `known_calories_kcal`：当天所有非空食物热量之和。
- `pending_item_count`：当天热量为空的食物项数，不是失败消息数。
- `meal_count`：当天有食物的早餐、午餐、晚餐餐别数量。同一午餐分两条记录仍计 1 餐。
- `other_count`：当天餐别为其他的饮食事件数量。
- 无记录时显示“今天还没有饮食记录”；不能显示成“今天摄入 0 kcal”。
- 全部热量为空时显示“已记录 2 项食物，热量待估算”；不能只显示合计 0。
- 部分已估算时显示“已知热量约 850 kcal，另有 2 项待估算”。
- 全部有热量时显示“已记录热量约 1150 kcal”。如果全部真实值为 0，则显示“已记录热量 0 kcal”。
- 日详情固定说明“仅统计已记录的食物”。不显示超标、剩余额度或缺餐警告。

## 9. AI 与图片配置

- 一组连接信息、四个模型角色，支持列表选择和手动输入。
- 文字、图片、连接检查和自动补算均只调用 Responses API；不提供其他生成接口或协议自动切换。
- 列表拉取不是实际模型调用成功，也不能仅据模型名称判断图片能力。
- 文字主备仅处理文字；图文消息使用图片主备，正常情况下一个模型完成识别、估算和操作提案，不再串接一次文字模型。
- 当前请求结束前可显示已选图片；处理结果和相关记录落地后移除图片，只留文字结果。
- 两个模型都失败时显示失败，不生成假记录；用户可重试、手动记录或放弃。

## 10. 回复风格

短、友好、事实清楚，不说教，不随意评价“吃得太多”“不健康”“今天表现不错”。可以少量使用聊天 emoji，不用 emoji 充当导航和设置图标。

可用回执：

- “已记录午餐：牛肉面，约 580 kcal。”
- “已改为半个苹果，约 48 kcal。”
- “已记录体重：132 斤。”
- “已经保存，热量待估算。”
- “AI 暂时不可用，可以重试或手动记录。”

“已记录 / 已修改 / 已删除”由 APP 根据提交结果生成；普通建议和必要的估算说明可使用 AI 的简短文字。
