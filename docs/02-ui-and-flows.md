# 02 页面与交互

## 1. 信息架构

```text
主界面
├─ AI 教练
│  ├─ 持续聊天、文字 / 图片发送
│  ├─ 记录回执 → 记录详情 → 编辑 / 删除
│  └─ 失败消息 → 重试 / 手动记录 / 放弃图片
├─ 日历 / 我的记录
│  ├─ 月历 → 某日饮食与体重
│  ├─ 记录详情 → 编辑 / 删除
│  └─ 手动新增 → 饮食 / 体重
└─ 我的
   ├─ AI 接口与四个模型角色
   ├─ 体重单位
   ├─ 备份 / 恢复
   ├─ 清除数据
   └─ APP 信息
```

主导航不增加统计、目标或独立补算页面。编辑和新增使用共享表单，避免聊天和日历维护两套规则。

## 2. AI 教练

### 2.1 布局

```text
┌────────────────────────────┐
│ AI 教练                    │
│ 今日已记录：2 餐           │
│ 已记录热量约 1150 kcal     │
├────────────────────────────┤
│             中午吃了牛肉面 │
│                            │
│ 已记录午餐，约 580 kcal。  │
│ [牛肉面 · 一碗 · 约580] ›  │
│                            │
│     晚上还吃了一个苹果     │
│ … 正在处理                 │
├────────────────────────────┤
│ [+] [说说吃了什么……] [发送]│
├────────────────────────────┤
│ AI教练    我的记录    我的  │
└────────────────────────────┘
```

- 顶部信息紧凑，不用大面积仪表盘挤占聊天。
- 用户气泡靠右，助手靠左；日期变化插入日期分隔。
- 用懒加载列表，首次载入最近 50 条，向上读取更早消息。界面分页与发送给 AI 的上下文范围分开控制。
- 新消息到达时：用户已经在底部就滚动到最新；用户正在读旧消息时展示“有新消息”，不强行跳转。
- 键盘打开时底部输入框保持可见；回到页面不清空草稿和未发送附件。
- 输入框支持多行，明确的发送按钮提交；不把换行自动当发送。
- V1 同时只处理一条前台聊天任务。可以继续编辑下一条草稿，草稿点击发送就是排队。
- 排队消息立即出现在聊天中并显示“排队中”，可以取消尚未开始的消息。每次点击发送提交当前草稿一次，不把按钮连点当成多条相同输入。
- 某条失败、需要澄清或本地保存失败时暂停后续队列，先显示重试 / 手动记录 / 回答问题入口，避免下一条“刚刚那个减半”改到错误对象。
- 澄清时输入框明确提示“回答上一条问题”，该回复优先处理；普通待发消息仍保留原顺序。用户也可以选择跳过当前事项后继续。

### 2.2 输入与图片

“+”展开拍照、相册、手动记录三个入口。相册选择与拍照累计最多 3 图，第四张给出“每条消息最多 3 张图片”，不静默丢弃已选内容。

- 有图片或非空文字之一即可发送。
- 待发送时显示缩略图、移除按钮和压缩进度。
- 发送前告知：图片和必要文字将发送给用户配置的 AI 服务，APP 成功处理后删除临时图片。
- 成功历史消息显示“发送了 2 张图片 · 已处理”，保留识别文字，不保留缩略图或可打开的原图。
- 图片识别为菜单、非食物或已形成可继续澄清的有效摘要时，保存文字结果后删除临时图；真正无法识别仍按失败保留临时副本。
- 请求失败时临时图仍可用于手动重试；若系统已清理文件，明确提示“图片已失效，请重新选择”，不能只用文字悄悄重试。
- 手动记录完成或用户放弃图片后删除对应临时图。

### 2.3 消息状态与动作

| 状态 | 展示 | 可执行动作 |
| --- | --- | --- |
| 未发送草稿 | 输入框和缩略图 | 编辑、移除图片、发送 |
| 已入队未开始 | 排队中 | 取消排队 |
| 主模型处理中 | 正在处理，可取消 | 取消，不允许连点发送 |
| 兜底处理中 | 正在尝试备用模型 | 取消 |
| 普通聊天 / 澄清 | 助手文字；必要时给候选记录 | 回复或选择候选 |
| 含图请求拟修改既有记录 | 显示目标与变更，暂停队列 | 确认修改 / 取消，不先落库 |
| 已保存 | 成功文字 + 可点击记录卡片 | 查看、编辑 |
| AI 全部失败 | “处理失败” + 简短原因 | 重试、手动记录、放弃图片 |
| 本地保存失败 | “识别完成，但未能保存” | 重试保存、直接编辑；不显示“已记录” |
| 用户取消 / 任务中断 | “已取消”或“处理已中断” | 手动重试或手动记录 |
| 已手动处理 | 原失败消息标为“已手动记录” | 打开生成的记录，不再显示 AI 重试 |

切换页面不等于取消已发请求。进入后台时已发出的单次请求可以完成保存，不启动下一条排队消息或新的补算；返回前台可继续未暂停的既有队列。进程重启后显示中断状态，由用户点击“继续队列”，不自动重发。

### 2.4 记录卡片

- 展示当前食物或体重值，绑定记录 ID，不复制一份不可更新的业务数据。
- 点击进入详情；消息含多餐或体重时分别展示关联卡片。
- 删除聊天卡片不影响真实记录。
- 已删除记录对应卡片显示“记录已删除”，禁用编辑入口。
- 不为每次记录加确认弹窗；仅在目标歧义或破坏性操作需要确认时询问。

## 3. 日历 / 我的记录

### 3.1 月历

- 默认当月、选中今天；支持上月 / 下月与回到今天。
- 橙色点表示有饮食，紫色点表示有体重；有两类记录就显示两个点。
- 有待估算食物仍然算有饮食，不等待 AI 恢复才打点。
- 选中日期、今天、记录标记采用不同视觉层级。
- 提供“饮食 / 体重”图例和可访问性日期描述，不仅依赖颜色。

### 3.2 当日详情

顺序：日期 → 已知热量与待估算数量 → 早餐 / 午餐 / 晚餐 / 其他 → 当日体重。

- 只展示有内容的餐别，不给没记早餐的人显示缺餐或红色空位。
- 食物项显示名称、份量（如果有）、约 N kcal 或“待估算”。
- 同餐别多次摄入按记录显示，不把两碗不同时间的面合成一条。
- 小计存在空值时显示“已知约 N kcal，另有 X 项待估算”。
- 当天多次体重全部列出：时间、数值、单位。未注明发生时间的记录明确标注，不拿录入时间冒充。
- 底部说明：“仅统计已记录的食物。”
- 页面提供始终可见的“新增”按钮，选择饮食或体重；离线也可用。

## 4. 详情、手动新增与编辑

### 4.1 饮食表单

| 字段 | 行为 |
| --- | --- |
| 食物名称 | 必填，普通文本 |
| 份量 | 可空，如半碗、一个、一小杯；不要求克数 |
| 热量 kcal | 可空；非负整数数字键盘；空值不是 0 |
| 日期 / 时间 | 新增默认当前场景日期；时间可选择“未注明” |
| 餐别 | 四个选项，当前分组或时间默认 |
| 备注 | 可空，收在“更多”区域，不增加必填项 |

入口可预填来源消息原文，名称仍由用户确认；不要把整段含多个食物的失败消息自动拆成若干条事实。需要多食物时用“添加食物”行，所有项目一起保存。

编辑餐的日期 / 时间 / 餐别时影响整餐；编辑单个食物时只改名称、份量、热量、备注。详情中清楚标注“本餐日期与餐别”，避免让用户误以为只移动其中一个食物。V1 不新增拆餐、跨餐拖动功能。

修改名称或份量后清空热量框，提示：“内容已变更，请确认热量；留空后会在 AI 可用时估算。”当次用户输入的热量随表单保存，不在后台先发 AI。

从已有记录直接编辑时展示原值，保存前用版本检查防止覆盖刚刚发生的聊天修改。发生冲突就提示刷新，不偷偷合并不同值。

### 4.2 体重表单

数值、斤 / 公斤、日期、时间。数值必填且为正数，最多两位小数；单位默认个人偏好。单位切换需要同步换算数值，不能把 66 公斤变成 66 斤。

### 4.3 删除与退出

- 详情删除先确认食物、整餐或体重，整餐确认框列出受影响项目数。
- 表单有未保存修改时关闭，询问放弃还是继续编辑。
- 表单保存中禁用重复提交；保存成功后返回原日期并刷新，日期改动时能看到目标日期。

## 5. 我的

### 5.1 AI 设置

接口类型固定显示为 Responses API，不提供协议切换选项。

```text
Base URL      https://example.invalid/v1
API Key       ••••••••••  [显示]
[拉取模型列表]

文字主模型       [列表选择 / 输入 ID]
文字兜底模型     [列表选择 / 输入 ID]
图片主模型       [列表选择 / 输入 ID]
图片兜底模型     [列表选择 / 输入 ID]

[检查所选模型]
```

- 模型选择支持搜索；列表拉取失败不清空已选 ID。
- 允许一个模型同时担任文字与图片角色；同一类型的主备必须是不同 ID，避免一次失败重复请求同一个模型。
- 设置尚未完成不阻止使用本地功能；发送时指出缺失的对应模型配置。
- 列表请求与真实模型检查分别显示结果。
- 点击“检查所选模型”前说明会发出实际请求，可能产生服务费用；检查四个角色时按唯一模型与模态去重，但分别显示对应结果。
- 文字检查通过 Responses 验证 completed 响应及简短 JSON 输出；图片检查使用同一接口和 APP 内置的非私人几何图验证 input_image，不用用户食物照片。
- 图片检查成功只证明接口能接收和理解该检查图，饮食识别质量仍由实际使用确认。
- 检查调用不写业务记录、不触发自动补算。每个角色单独显示通过或失败，不能用兜底成功遮住主模型配置错误。

### 5.2 数据管理

- 体重显示单位：斤 / 公斤，不增加个人资料。
- 备份：保存本地文件，展示导出日期与食物 / 体重 / 消息数量。
- 恢复：先预览备份信息与数量，明确“将替换当前记录，不合并；AI 接口设置保持不变”。确认后恢复。
- 恢复前自动保存一份当前数据到 APP 私有安全副本；如存在该副本，数据管理中显示“恢复上次替换前的数据”入口。
- 安全副本只保留最近一份，下一次替换前更新。清除全部数据也会删除它。
- 清除全部数据单独放在页面末尾，确认框说明聊天、记录、设置、Key、临时图片和内部安全副本都会被删除；已经导出的外部备份不会被 APP 自动删除。
- 基本信息：版本号、数据格式版本、隐私说明。

## 6. 自动估算的反馈

- 有待估算项目时保留在对应日期，不移到恢复联网那天。
- 自动估算不占用聊天输入。用户发新消息时，暂停 / 取消正在进行的补算，优先处理用户消息。
- 前台可用一条低干扰状态提示“正在补充 3 项食物的热量”，提供“停止本次”。不弹等待对话框。
- 完成后提示“已补充 3 项食物的估算热量”；还有无法估算的项目则保留“待估算”和原因。
- 用户修改、填写热量或删除记录时，相应旧补算结果不能覆盖新值。
- 自动补算的完成不能再次触发自身，不形成请求循环。

## 7. 视觉规范

采用浅色、轻量、内容优先的原生移动端风格。V1 不增加主题切换或单独深色主题。

| 语义 Token | 建议值 | 用途 |
| --- | --- | --- |
| `surface` | `#FFF9F3` | 奶油白背景 |
| `surfaceContainer` | `#FFFFFF` | 表单、详情与必要分组 |
| `primary` | `#72506B` | 主要按钮、选中态 |
| `onPrimary` | `#FFFFFF` | 主按钮文字 |
| `onSurface` | `#2B292D` | 主体文字 |
| `onSurfaceVariant` | `#625B63` | 次要说明 |
| `peachSoft` | `#F9E3D8` | 用户气泡、柔和强调 |
| `purpleSoft` | `#EFE6F6` | 体重区域辅助色 |
| `mintSoft` | `#E4F2E7` | 已完成状态辅助底色 |
| `foodMarker` | `#C46C35` | 日历饮食点 |
| `weightMarker` | `#865CC0` | 日历体重点 |
| `error` | `#A83232` | 请求或输入错误，配文字说明 |

- 浅色仅用于背景与点缀，正文使用深色；不把浅桃色文字直接放在白底上。
- 使用 Android 系统中文字体，不远程加载字体。正文 16sp、辅助 14sp，标题 20–24sp，热量主值 24sp；不靠缩小文字塞进更多内容。
- 间距遵循 4 / 8 / 12 / 16 / 24dp；页面水平留白 16dp，常规卡片圆角 16dp，气泡圆角 16–20dp。
- 交互区域至少 48×48dp，图标可小、命中区不能小；导航同时有图标和文字。
- 使用 Flutter Material 图标，不新增一套图标依赖；聊天语气中的 emoji 与界面图标分开。
- 仅真实分组使用卡片，不给每一行都加边框和阴影。
- 动效只反馈展开、切换和提交状态，约 150–250ms，尊重系统减弱动画设置。
- 适应系统大字体、屏幕阅读器、键盘和底部手势区；日期标记、按钮、输入框都有可理解标签。

界面实现后重点验收窄屏、大字体、键盘弹出时的阅读与操作，按06的A32记录真实结果。
