# 05 可靠性与数据安全

## 1. 不可破坏的规则

1. AI 只提供提案，数据库是业务事实来源。
2. 本地事务提交之前不显示“已记录 / 已修改 / 已删除”。
3. 主备、重试、迟到响应不能使同一个操作重复产生数据。
4. 直接编辑、聊天修改和自动补算都使用版本检查；自动补算只填空值。
5. 图片清理只针对 APP 创建并登记的私有副本，不删除相册或外部路径。
6. 恢复备份失败不先清空当前数据；Key 不随业务备份流转。

## 2. 聊天操作状态

```text
保存原消息 → pending → in_flight
                         ├─ 主失败 → 同一操作的兜底请求
                         ├─ 全部失败 → failed
                         ├─ 用户取消 → cancelled
                         └─ 有效提案 → ready
                                         ├─ 提交成功 → committed
                                         └─ 保存失败 → 保持 ready，供本地重试

进程中断：pending / in_flight → interrupted
手动重试：failed / interrupted → in_flight，同一操作 ID、新请求代次
本地重试：ready → committed，不重新调用模型
```

`committed` 包含普通聊天、澄清和业务操作完成，不表示每次都新增饮食。结果类型、业务 ID、图片摘要和回执记录在 `receipt_json`。

### 2.1 发送之前

- 点击发送时为原消息分配一次 `operation_id`、消息 ID、递增 queue_order，保存当时参考时间；即使要排队也先持久化。
- 图片先准备好私有副本和登记行，再将消息状态写为可发送；图片准备失败不发残缺请求。
- 原消息与操作保存失败时留在输入框，提示本地存储问题，不继续发 AI，也不假装已经可靠保存输入。
- 点击发送后禁用该操作的再次提交。用户重新发一条相同内容属于新的输入，不能按文字相同擅自去重。

### 2.2 前台串行队列

- 允许连续提交新消息，但同一时刻只有一个正常聊天操作进行主备请求。
- 按 queue_order 取下一条，执行时重新构建记录快照；这样后发的纠正可以看到前一条刚保存的记录。
- 当前请求的上下文排除后续排队输入，不能把未来消息提前识别和记录。
- 失败、版本冲突、需要澄清、本地保存失败均暂停后续队列。重试 / 手动处理完成后继续；用户也可明确选择“跳过并继续”。
- 澄清回答通过 reply_to_operation_id 插在当前暂停点处理，不排到其他待处理消息之后；成功后恢复原 FIFO 队列。仍需澄清时继续暂停。
- 澄清回执保留 resolution（open / answered / skipped）和可空 resolved_by_operation_id。回答完成后在同一事务中关联原问题；若回答又产生新问题，由新问题继续暂停。明确跳过时结束当前所属澄清链，重启后不再次卡在已处理的问题上。
- 取消尚未开始的消息只取消该操作和其图片；不影响前后独立消息。后续依赖这条消息的指令仍需重新定位或澄清。
- 应用在后台不启动新的排队请求；已发单次请求的结果可保存，下一步兜底或下一条在前台继续。进程重启后未完成队列改为 interrupted，保留顺序，由用户点击继续，不自动重放。

### 2.3 请求代次和迟到结果

每次真实请求携带 `(operation_id, request_generation)`。换到兜底、手动重试、取消时推进代次；只有当前代次且操作尚未提交的响应才可进入解析与保存。

恢复、清除全部数据时再推进内存级 `data_epoch`，使之前发出的所有回调失效。即使网络无法立即取消，旧响应也不能写进替换后的数据库。

### 2.4 保存提案与提交

1. 解析外部响应，校验协议、字段、引用与用户意图。
2. 把已校验提案保存到 `plan_json`，状态置为 ready。网络步骤到此结束。含图提案涉及既有记录修改 / 删除时，由客户端在计划中标记 requires_user_confirmation，暂停队列，展示目标与变更；未确认不能进入提交步骤，本地重试也不能绕过确认。
3. 开启事务，再读操作状态：已经 committed 就取既有回执，不执行动作。
4. 校验本次涉及的初始记录 / 餐版本和目标存在性。
5. 应用全部动作，更新对应版本，清除被删空餐。
6. 从真实变更生成回执和记录引用，写入或更新该操作的助手消息。
7. 同一事务将操作置为 committed，并将可清理图片标为 delete_pending。
8. 提交完成后通知页面刷新，再执行文件删除。

事务失败时全部业务变化回滚。保留 ready 提案与可见的失败提示；“重试保存”只重做本地提交，不因磁盘问题重新请求模型。

`origin_operation_id + client_ref` 的唯一约束是新增实体的额外约束，操作状态是主要去重入口；不得用 `INSERT OR REPLACE` 吞掉冲突并覆盖已有实体。

### 2.5 版本冲突

普通聊天若有任一目标版本已变或被删除，整次提案不提交，并失效该旧计划。提示“记录刚刚有变化，请确认后再修改”，提供查看当前记录入口。

刷新后的重新请求仍对应同一未提交逻辑操作，使用新代次和新快照；这属于用户主动重试，不属于自动换模型。已提交操作则永不重新执行，哪怕其记录后来被用户删除。

### 2.6 失败后手动处理

- 从失败消息打开表单时携带原 `operation_id`，预填原文字。
- 保存前确认原操作尚未 committed，并取消 / 失效其残余请求。
- 将手动内容按同一个操作提交，成功后消息标为“已手动记录”，关联新记录。
- 手动完成后隐藏该消息的 AI 重试入口；即使迟到回调到达，也只能看到已提交状态。
- 从日历独立新增则生成新的本地操作 ID。
- 用户只想问问题、无需记录时可以保留失败消息或删除，不强迫打开手动表单。

## 3. 自动补充空热量

### 3.1 触发条件

同时满足：

1. APP 在前台。
2. 一次用户正常聊天经主或兜底得到有效结果，并完成本地结果保存。
3. 数据库存在 `calories_kcal IS NULL` 的食物。
4. 本次没有正在运行的补算。

正常消息队列必须已清空且没有暂停待处理事项。有后续消息时记下本次触发意图，先处理完整个前台队列，再读取一次待估算快照。

文字聊天或图片聊天成功都可以触发；实际补算使用文字主备。拉取模型列表、设置页模型检查、补算自己的成功，不作为触发源。

不在恢复网络、开机、后台、定时器或系统任务里探测服务。没有下一次正常 AI 使用时，待估算记录可以一直保留。

### 3.2 本次处理范围

- 触发时读取所有日期待估算 ID 的快照，按录入顺序处理，不只处理今天。
- 每批最多 10 个食物，串行处理本次快照；新产生的空值留到下一次触发。
- 发送前重新读取当前名称、份量、热量、版本，已删除或已有值的剔除。
- 优先使用当前食物字段；原始描述仅作补充，不能用“一整碗”的旧描述推翻用户后来改的“半碗”。
- 每批主模型一次、失败再兜底一次。批次仍失败就结束本次补算，不继续请求后续批次。
- 模型返回某项确实无法估算的 null 是正常结果：保留该项，继续处理本次快照中的其他项，不把同一项在本轮反复重试。

每批的两次调用上限与正常聊天相同。待估算很多时会产生多批请求，前台应显示数量并允许停止本次；不隐藏为一次“免费连接检查”。

### 3.3 写入条件

本批有效结果放在一个本地事务中处理，但逐项做条件更新：

```sql
UPDATE food_items
SET calories_kcal = ?,
    calorie_source = 'ai',
    estimation_note = ?,
    version = version + 1,
    updated_at_ms = ?
WHERE id = ?
  AND version = ?
  AND calories_kcal IS NULL;
```

- 更新数量为 0 就跳过该项，不能再用无条件 UPDATE 覆盖。
- 当前已经由用户填写、被聊天更新、被删除或版本变化的项目均跳过。
- 成功项更新所属餐版本，收集原日期，事务提交后刷新其汇总。
- 对返回 null 的项目，可以在同样条件下保存无法估算的简短原因，热量仍为 NULL、来源仍为 unknown；不得记成成功补充热量。
- 本批操作提交状态和实际成功 / 跳过项放入回执。重复执行同一批提交只返回已有结果。
- 不修改任何日期、餐别、食物名称、份量或用户备注，不新增食物，不动体重。

### 3.4 前台优先与中断

- 用户发送新消息时中断当前补算请求，失效其代次，先处理新消息。
- 用户在本地编辑或删除某项时无需等补算；条件更新负责保护结果。
- 应用进入后台、用户停止本次、开始恢复或清空数据时，不启动下一批，并取消当前批请求。
- 已提交批次保留；未提交项目仍为空。下一次正常聊天成功后重新读取剩余项目。
- 不添加持久后台任务表：空值本身就是待估算条件，操作账本负责批次去重。

## 4. 图片生命周期

### 4.1 创建与发送

1. 系统选择器返回文件或拍照结果。
2. APP 只读取该来源，转为独立 JPEG 副本；修正像素朝向，不保留来源 EXIF / GPS。
3. 默认以长边约 1600 像素、质量 85 为压缩起点；小图不放大。宽高参数按插件实际比例计算，不把 `minWidth` 名字误解为硬性最长边。
4. 客户端初始限制：压缩后每张最多 5 MiB，单条最多 3 张。仍超限时提示换图，不无限降低质量直到无法识别。这是客户端上限，不保证服务一定接受同等大小。
5. 私有 `pending-images` 目录只使用 APP 生成的 UUID 文件名。登记相对路径、消息归属、大小和 MIME。
6. Base64 只在构造当前请求时存在内存中，不写进 SQLite 或日志。

`image_picker` 的 Android 活动重建需使用其丢失结果恢复入口；恢复出的图片回到待发送状态，不自动发送。[维护者说明](https://pub.dev/packages/image_picker)

### 4.2 何时删除

| 事件 | 处理 |
| --- | --- |
| 已识别，相关记录与文字结果提交成功 | 标记 delete_pending，删除 APP 副本 |
| 已识别为菜单 / 非食物，或可用摘要足以继续文字澄清 | 保存有效文字摘要后删除副本 |
| 主备都失败 / 都无法识别 | 暂存，供用户重试、补充文字、手动记录或放弃 |
| 识别成功但本地保存失败 | 暂存，等待重试本地保存 |
| 用户完成关联手动记录 | 删除该失败任务的 APP 副本 |
| 用户取消发送、放弃图片、删除对应聊天 | 删除对应 APP 副本 |
| 用户清除全部数据 | 删除全部 APP 图片副本 |

图片删除不受是否记录了热量影响，而由“本次识别已得到可保存结果 / 用户结束任务”决定。真正无法识别属于失败，不靠一个格式正确的 JSON 就认作识别成功。

### 4.3 文件删除与数据库事务

文件系统不能参加 SQLite 事务。先在结果提交事务中标记 delete_pending，再删除文件；成功后移除附件行。文件已经不存在视为删除已完成。

启动时处理 delete_pending，并清理该私有目录内未被任何活动附件引用的孤立副本。不得扫描相册、外部备份目录或用模型给出的路径删除文件。所有最终删除路径必须解析后仍处于 APP 自己的 pending-images 根目录内。

历史只保留 `image_count` 与必要识别摘要，不保留图片内容、缩略图、原始来源路径。图片缺失不影响已有记录查看。

## 5. 失败类型与用户操作

| 失败 | 用户文案方向 | 行为 |
| --- | --- | --- |
| 未配置连接或对应主备模型 | 请先完成 AI 设置 | 不发网络，保留草稿，可手动记 |
| Key / 权限错误 | 接口未授权，请检查 Key 和模型权限 | 本轮按固定主备结束后提示，不无限尝试 |
| URL / 模型不存在 | 接口或模型不可用，请检查设置 | 保留配置和原文字 |
| 超时 / 无网络 / 限流 / 服务错误 | AI 暂时不可用 | 主备后失败；重试或手动记录 |
| JSON / 操作协议不合法 | 模型没有返回可用的记录结果 | 主备后失败；不靠文本猜测写入 |
| 图片均无法识别 | 无法识别，请补充文字或手动记录 | 不生成食物；临时图可手动重试 |
| 目标记录有多个候选 | 你指的是哪一条 | 正常澄清，不算网络失败 |
| 目标已变化 / 删除 | 记录刚刚有变化，请确认后再修改 | 不覆盖，不换模型 |
| 磁盘满 / SQLite 保存失败 | 识别完成，但未能保存 | 保留提案，提供重试保存 |
| 图片临时文件失效 | 图片已失效，请重新选择 | 不偷偷变成纯文字请求 |
| 备份格式或版本不支持 | 无法恢复这份备份 | 保留当前数据 |

错误详情可包含 HTTP 状态、模型 ID、脱敏服务错误摘要；不显示 Authorization、完整 URL 凭据、图片字节或完整请求体。未识别错误保留明确失败，不捕获后返回假成功。

## 6. 本地备份格式

### 6.1 格式和内容

V1 使用 UTF-8 JSON 文件，建议名 `food-journal-YYYYMMDD-HHmm.foodjournal.json`，不需要 ZIP 或密码管理界面。

```json
{
  "format": "food-journal-backup",
  "format_version": 1,
  "database_schema_version": 1,
  "exported_at": "2026-10-19T12:00:00Z",
  "preferences": {"weight_unit": "jin"},
  "operations": [],
  "chat_messages": [],
  "meals": [],
  "food_items": [],
  "weight_records": []
}
```

各表数组使用 03 中对应字段的可导出表示。导出事务取得一致快照；不直接复制一个正在写入的数据库主文件，避免漏掉日志中的数据。

包含完整聊天文字、饮食、体重、必要操作 ID 与已提交回执、单位偏好。排除：

- API Key、安全存储内容；
- 整组 AI 接口配置，包括 Base URL、模型 ID、HTTP 风险确认；
- 所有图片、缩略图、附件文件路径、未发送附件和草稿；
- 原始网络日志、未提交提案和能自动重放请求的状态。

所有导出操作的 `plan_json` 置 null；非 committed 操作统一归一为 interrupted，并移除活动请求信息。对应 queued / processing 消息归一为 interrupted。已提交操作的业务 ID 与回执保留，用于恢复后的去重和卡片关联。

导出的 JSON 本身包含私人饮食与体重明文，保存前提示妥善保管。用户可以通过系统选择器主动保存到其选择的位置；APP 不自动上传备份。

### 6.2 导出流程

1. 短暂阻止本地提交，事务内读取需要导出的完整快照。
2. 在私有目录生成完整临时 JSON，写入完成后才打开系统保存对话框。
3. 用户选择位置并成功保存后显示完成；取消只结束导出，不清除源数据。
4. 删除导出中间文件，不保留无限历史副本。

### 6.3 恢复流程

恢复为整库业务数据替换，不合并：

1. 选择文件，检查格式标识、版本、完整 JSON、字段类型、重复 ID、引用完整性、热量空值 / 来源对应、体重换算一致性。
2. 外部文件不可信，不执行 SQL，不根据其中的路径读写其他文件。初始文件大小上限为 100 MiB；超出时明确提示不支持，不截断导入。
3. 预览日期、消息 / 食物 / 体重数量，说明当前数据将被替换、AI 设置和 Key 保持当前设备值。
4. 用户确认后暂停所有请求、补算与本地提交，推进 data_epoch，取消旧回调。
5. 将当前可导出数据写成私有安全副本；副本写入失败则停止恢复，不先替换。
6. 在单个数据库事务中清除旧业务表、插入已验证内容、恢复单位偏好，保留当前 `ai_profile` 和安全存储。删除旧草稿；不导入附件。
7. 事务失败则完整回滚，当前业务数据仍可用。恢复成功后清理旧图片，刷新全部页面。
8. 导入的中断操作不自动发请求。空热量仍是待估算，等下一次正常 AI 成功再处理。

最近一份替换前安全副本通过数据管理页的“恢复上次替换前的数据”入口使用，仍需预览和确认。恢复安全副本前同样保存当前快照，便于撤回误操作。安全副本在卸载或清除 APP 数据时会丢失，不能代替用户导出的备份。

本版只支持 format_version 1、schema 1。未来增加迁移时再扩展；遇到更高版本先拒绝，不尝试删字段凑兼容。

## 7. 凭据与隐私

- Key 使用 `flutter_secure_storage` 保存，并绑定规范化 Base URL。编辑地址后须重新确认对应凭据。
- 不硬编码开发者 Key，不为用户代管 Key，不将其加入任何文档、源码或异常日志。
- 默认 HTTPS；HTTP 的风险确认只解决明文使用的知情选择，不允许忽略 HTTPS 的无效证书。
- 只向配置服务发送当前任务必要文字、压缩图片与必要历史候选。不默认上传整库记录。
- 自动估算只发本批次食物资料。设置页检查使用非私人检查内容。
- 所有生成请求采用 Responses API，显式 store=false，不建立远程会话，也不把服务端 response_id 作为历史依赖。
- 设备上删除图片只作用 APP 副本；外部 AI 服务的日志与保留规则由该服务决定。首次使用说明要把“本地保存”和“外部处理”讲清楚。
- 不接入广告、分析 SDK 或崩溃内容上传；日志只保留定位问题必要的错误类型、耗时和非敏感标识。

Android 平台自动备份与用户手动导出是不同入口。清单显式关闭默认云备份，并按 Android 版本配置 backup rules / data extraction rules，排除数据库、偏好、凭据、私有副本和临时图；同时处理云备份与设备迁移规则，不能只写一个 allowBackup 标记就声称覆盖所有设备行为。[Android 官方说明](https://developer.android.com/identity/data/autobackup)

## 8. 清除全部数据与启动恢复

### 清除全部数据

二次确认后取消所有任务、失效回调，删除业务记录、聊天、设置、Key、图片和内部安全副本。清除动作不先暗中保留一份新的安全副本。外部已导出的备份不在删除范围内，确认文案明确说明。

数据库和安全存储不是同一事务；清除服务分别记录结果，任一步失败就明确指出尚未清除的类别，允许继续完成，不显示“全部清除成功”。不要靠重建数据库来掩盖其他清理失败。

### 启动恢复顺序

1. 打开数据库并确认 schema；失败时保留文件并显示问题，不自动重置。
2. 把未完成网络操作置为 interrupted；ready 提案保留供本地重试。
3. 清理 delete_pending 和明确孤立的私有图片。
4. 接收系统图片选择器的丢失结果，回到草稿，不自动发送。
5. 恢复聊天和记录显示。没有用户动作时不发 AI，也不启动自动补算。
