# 05 可靠性与数据安全

## 1. 不可破坏的规则

1. AI 提供提案，SQLite 当前有效记录是事实。
2. 完整响应未到、本地事务未提交，不显示成功卡片或成功回执。
3. 每个独立子事项可提交、重试、撤销；成功项不被失败项回滚，不被整条重试重复执行。
4. 版本变化、取消、恢复和清除后，旧响应不能写入。
5. 补算只填仍为空的字段，不动已有值、日期、名称或份量。
6. 长期资料须授权，图片只删 APP 副本，Key 不随备份流转。

## 2. 消息、阶段和子操作

```text
保存用户输入 → pending → running（vision / text / lookup）
                          ├─ 当前阶段主失败 → 对应兜底一次
                          ├─ 均失败 → failed（保留文字 / 已成功摘要）
                          ├─ 停止 → cancelled 或 partial
                          └─ 完整提案持久化 → ready
                               ├─ 独立action逐项事务提交
                               ├─ 待补充 / 待确认保留
                               └─ 全部完成 completed / 部分完成 partial
```

operations 是消息整体 / 阶段状态，operation_actions 是执行事实，两者不能混用。普通聊天无业务动作也可 completed；partial 明确列出成功、失败、待处理项，不冒充全部完成。

### 发送与前台队列

- 入队事务分配稳定 operation_id、消息 ID、递增 queue_order、参考时间、上下文和附件归属。失败保留草稿，不发请求、不假装输入已安全保存。
- FIFO 前台单任务，执行时刷新事实；后续排队消息不提前混入当前上下文。
- 网络失败、待回答、资料待确认不永久堵塞独立后续消息。当前事项转非运行状态后继续下一条；不并行修改数据。
- 定向回答携带 reply_to_action_id，优先恢复该待处理事项；其他普通消息仍按原顺序。没有明确关系时不把输入当任意旧问题答案。
- 后续指向失败或取消对象时澄清，不错改之前同名记录。没有可用对象就不提交修改。
- 后台不启动新阶段、兜底、排队消息或补算。已发单请求可完成摘要持久化 / 提案和本地提交；后续网络阶段等回前台。
- 进程重启：running / pending 归 interrupted，保留阶段、摘要和顺序，用户点击继续；ready 计划可重试本地提交，不重调模型。

### 请求代次

每次真实请求使用 operation_id、stage、request_generation，换兜底、重试、取消推进代次。当前代次且未终止的响应才能进入计划处理。恢复 / 清除再推进内存 data_epoch，全部旧回调失效。

D03 暂定两阶段：视觉摘要校验后事务保存，附件标 delete_pending，再删图。文字阶段失败复用摘要；视觉已成功不会因后续失败重新调用图片模型。摘要不足再让用户补充，不读取已删图。

## 3. 完整计划与逐项提交

1. SSE 完成或非流式 completed 后校验整个 envelope；残缺或整体非法不执行任何动作。
2. 逐项校验，客户端分配 action_id，并持久化不可重排的计划。无效项有明确失败结果，其他独立有效项仍可执行。
3. 一餐和食物、同餐互相依赖的变更先合成完整单位。不能将同一快照版本的互相覆盖动作拆成独立事务后覆盖。
4. 每个 ready 项事务内重读 action 状态和全部目标当前版本；已 committed / undone 只返回原回执。
5. 保存 before 快照，应用变更并递增版本，保存 after / result，置 committed；同步更新助手回执中的该项。
6. 提交后刷新相关旧 / 新日期与卡片；继续独立项。事务失败只回滚该单位，标记失败并保留计划，不能把其他成功项回滚。
7. 汇总 operation 状态。任何未完成项继续可见，不能只用“消息成功”隐藏。

本地保存失败不触发模型兜底。“重试保存”只重做该事项本地事务。版本冲突使旧项失效，提示查看当前记录；用户明确重新请求后，按未完成范围重建提案，不自动赌另一个模型。

技术去重依靠 action 状态与 origin_action_id + client_ref 唯一约束，不能用 INSERT OR REPLACE 吞冲突。内容相似由 AI 简短询问，明确“又吃一份”是新的操作，不按原文散列去重。

### 追问、确认和手动处理

- 追问保留原 action 与参考时间，新的回答消息关联它；只替换该未完成计划，不重建其他成功项。
- 资料保存 / 更新通过 consent_proposals 等用户确认，不阻塞本餐或后续独立消息；同意才形成 local action。
- 失败卡打开手动表单带原未完成 action_id。事务前失效该项残余请求，保存为同一事项；手动完成后隐藏完整重跑入口。
- 原消息完全未形成计划时，手动提交创建本地动作并完成该输入，不能之后再对同一输入整条自动记账。
- 已成功部分保留，只提供未完成部分手动处理，不让用户再次录入已保存的一餐。

## 4. 停止与撤销

### 停止

停止推进请求代次并取消当前网络；标记未提交项取消，已提交项保留；后续独立队列继续。停止不删除记录、不撤销成功项。

SQLite 提交不可在事务中途被 UI 按钮强行打断。停止发生在提交前则拒绝进入；事务已经提交则保留并显示实际结果，提供撤销，不谎称没有保存。

### 撤销

本地和聊天撤销都先定位具体 committed action。读取 before / after 和当前对象版本；只有全部对象仍符合该 action 提交后的状态，才能逆向执行这个单位。

创建独立 undo operation / action，事务内校验版本、恢复业务字段 / 软删除状态、递增当前版本，标原项 undone，并保存撤销回执。新增的逆操作是软删除；删除的逆操作恢复同 ID；修改恢复原字段，不回退版本号。

有后续变更时拒绝直接覆盖，提示当前记录，允许用户通过新编辑明确恢复所需字段；不自动串联撤销所有后续操作。重复点同一撤销返回原结果，不反复翻转。恢复被删餐时同时恢复当时该操作影响的食物，不恢复原本已经删除的其他项目。

操作历史属于完整备份内容。清除聊天不删历史；清除全部数据才一并清除。不新增版本树、任意版本回滚 UI 或无依据的定时历史清理。

## 5. 缺失营养自动补算

触发条件：前台正常用户聊天有效完成本地结果保存；有缺失营养；当前用户 FIFO 无可运行事项，且不在补算。资料待确认不阻止独立补算；有用户正在回答的事项或活动请求时先让出。

模型列表、能力检查、网络恢复事件、启动和补算自身成功不触发。所有日期的有效食物纳入触发时快照，每批最多10项，串行；新空值留下一轮。每批 text 主一次、兜底一次，均失败结束本轮，不继续请求后批。

请求前重读当前字段和版本，只请求仍缺失字段。已有热量但缺脂肪时仅补脂肪；已有值不因来源为 AI 就重新估。返回 null 是无法合理估算的有效结果，留原因，不反复请求同项。

事务中每食物校验当前 version、未删除、餐未删除，对每个允许字段使用 `... WHERE id=? AND version=? AND field IS NULL` 的条件语义；实现可读行后合并空字段并一次带版本 UPDATE，不能无条件覆盖。成功更新的食物与餐版本递增，来源和依据仅更新填入的字段。

每批记录实际成功、跳过、仍未知结果；重复批次返回既有结果。用户消息、新编辑、后台、停止、恢复或清除优先中断请求 / 后续批次。已完成批次保留，下一次有效触发从剩余缺失读取。不建立后台轮询或持久无限任务队列。

## 6. 图片生命周期

### 准备

系统相机 / 相册返回来源，只读取，生成 APP 私有 UUID JPEG 副本、修正朝向、去 EXIF / GPS。保守压缩初始长边约1600、质量85，小图不放大。压缩后每图上限5MiB、每消息3图，这是客户端限制，不代表服务保证。

营养表数字优先清晰；过大时提示换图，不无限降低质量。插件 minWidth / minHeight 按实际比例计算，不能误当最长边。Base64 仅请求内存，不写 SQLite / 日志。活动重建用 image_picker 的丢失结果恢复到草稿，不自动发送。

### 删除时点

| 事件 | 处理 |
| --- | --- |
| 有效视觉摘要 / 可继续澄清摘要落地 | 标记后删 APP 副本，再继续文字阶段 |
| non_food / 菜单 | 保存必要说明后删副本 |
| 视觉主失败、正准备同阶段兜底 | 暂留供唯一兜底 |
| 视觉主备均失败 / 无法识别 | 终止本次识图并删副本，保留文字和重选入口 |
| 摘要尚未本地保存成功 | 暂留，提示重试本地保存；不继续文字阶段 |
| 用户停止、放弃、删聊天或清空数据 | 删除对应 APP 副本 |
| 用户未发送草稿 | 暂存并登记，移除或丢弃草稿后删 |

先事务保存摘要和 delete_pending，再文件删除，成功后移除附件行。文件系统不参加 SQLite 事务；启动补清 delete_pending 和私有根目录内明确孤立副本。

删聊天前先记录其附件清理清单，再删行；不靠已级联删除的附件行找文件。最终路径须解析后仍在 APP pending-images 根目录，不接受模型或备份文件中的路径。相册原图、外部备份永不自动删除。

只有有效摘要落地才算识图成功，格式正确但内容是无法识别不算成功。图已删除、摘要不足则补文字或重新选图，不假装还能查看。

## 7. 错误与恢复入口

| 情况 | 行为 |
| --- | --- |
| 配置不全 | 不请求，保留输入，可手动记 |
| Key / 服务账户错误 | 清楚指出检查配置，避免无意义兜底 |
| 单模型超时 / 模型错误 / 整体协议错误 | 当前阶段对应兜底一次，仍失败手动重试 |
| SSE中断 | 不提交未完成计划，标中断文字，兜底替换同一回复 |
| 识图成功、文字失败 | 留摘要，重试文字，不重传图 |
| 单项非法 / 版本冲突 | 仅该项失败，独立成功保留 |
| 磁盘满 / SQLite失败 | 未保存无成功回执，仅重试本地 |
| 原图已清理 / 文件缺失 | 明确重选，不悄悄退成纯文字识图 |
| 备份损坏 / 密码错误 / 不支持版本 | 不替换当前数据 |

详情可含HTTP状态、模型ID、脱敏错误和耗时，不含 Authorization、完整请求体、图片字节或 Key。错误不能静默改成默认成功。

## 8. CSV、完整备份与加密

### CSV

分别导出饮食和体重。饮食每食物一行：日期、可空时间、餐别、名称、份量、热量、三营养、各来源、备注；体重含日期、时间、原值原单位、统一公斤。未知留空，不写0。

UTF-8、正确引号 / 换行转义；文本单元格以制表符、回车开头，或去除前导空白后以 =、+、-、@ 开头时加文本保护，不改数值字段。CSV 不含聊天、完整撤销关系或 Key，不用于完整恢复。

### 完整明文内容

```json
{
  "format":"food-journal-backup","format_version":1,"database_schema_version":1,
  "exported_at":"2026-10-19T12:00:00Z",
  "preferences":{"weight_unit":"jin","theme_mode":"system","onboarding_completed":true},
  "operations":[],"operation_actions":[],"chat_messages":[],
  "meals":[],"food_items":[],"weight_records":[],
  "food_library":[],"ai_memories":[],"consent_proposals":[]
}
```

一致读事务生成快照，包括软删除数据、撤销历史、拒绝建议状态、授权资料和必要引用。排除 Key、整组 AI 地址 / 模型配置、全部图片 / 路径 / Base64、草稿、原始请求和可自动重放活动状态。

导出保留子操作 ID、committed / undone / 授权关系；未完成网络 operation 归 interrupted，未提交 action 归 failed 并记录 needs_replan，移除其 plan / payload，保留用户可读说明和未完成范围。待同意的 consent_proposals 可保留，但导入后不自动执行。恢复后由用户发起重试，基于当前未完成范围重新请求，不重复成功项；不能把空payload当可重试本地计划。

### 可选密码

无密码文件为UTF-8 JSON并提示私人明文。加密文件 `.foodjournal.enc.json` 是明确版本的 JSON 信封：format、version、kdf、salt_base64、nonce_base64、ciphertext_base64、tag_base64。

本项目初始约定 PBKDF2-HMAC-SHA256、600000次、随机16字节盐派生32字节Key，AES-256-GCM、随机12字节nonce、16字节tag；用成熟库，不自写算法。信封格式 / 算法 / KDF参数作为认证附加数据，版本1只接受约定参数，不运行导入文件任意指定的超大迭代数。密码不保存，不能找回。

导出中间文件放私有目录，系统选择器保存完成才提示成功，取消不改源数据；随后清中间文件。密码错误 / 认证失败不暴露部分明文、不继续解析恢复。初始导入文件上限100MiB，解密后的内容也设100MiB上限，超出拒绝不截断。

## 9. 恢复和清除

恢复为整库业务替换，不合并：

1. 文件大小和信封检查，必要时解密；完整校验格式、schema、字段、唯一ID、引用、子操作状态、营养来源和体重换算，不执行SQL或文件路径。
2. 预览日期和消息 / 食物 / 体重 / 资料数量，明确替换、AI配置和Key保持当前设备值。
3. 用户确认后暂停请求和提交、推进data_epoch。先写最近一份替换前安全副本，失败则停止，不清当前库。
4. 单事务按外键顺序替换业务表和必要偏好，保留当前AI设置 / 安全存储。循环语义引用分两步插入关系，不关闭外键后放任坏引用。
5. 失败回滚当前数据，成功清理旧图 / 草稿并刷新页面；不自动重放网络。缺失营养等下一次正常成功后补。

内部安全副本是APP私有一致快照，可通过“恢复上次替换前的数据”预览恢复，只保留一份。它不含Key，不替代外部备份，卸载会丢失；不暗中上传。

清除全部数据需确认：中断 / 失效任务，删除聊天、记录、操作、食品资料、偏好、建议、设置、Key、图片、内部安全副本。外部导出不动，清除前不偷偷再保留副本。SQLite、凭据、文件不是同一事务，分别记录结果，部分失败准确说明并允许继续，不报假全部成功。

## 10. 隐私和启动

只发送当前任务必要上下文、授权资料和临时图片，不上传全库。store=false 只表达不依赖可检索响应存储，不等于第三方服务零日志承诺。首次说明本地保存与外部AI处理的区别。

不接广告、分析或聊天崩溃内容上传。Android关闭默认云备份，并按系统版本配置云备份和设备迁移排除数据库、偏好、凭据与私有文件；不只写allowBackup就声称所有厂商迁移行为已验证。

启动：安全打开schema（失败保留文件）→归一中断任务→清理待删 / 孤立图片→恢复选择器丢失结果到草稿→展示本地数据。不因启动自动发AI或补算。
