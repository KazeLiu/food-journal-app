# 06 开发计划与验收

## 1. 当前交付与实施目标

本次完成开发文档，尚未创建 Flutter 工程、安装依赖、调用真实模型或实现 APP。

实施目标是做出可长期使用的轻量个人记录工具，不是先拼出能聊天的壳。开发按“离线数据路径 → Responses 文字记录 → 图片 → 自动补算 → 数据恢复”推进，每一步复用同一套记录与提交逻辑。

应用工程放在项目的 `app/` 子目录，根目录 README 和 docs 继续用于开发文档。显示名暂用“饮食记录”，applicationId 暂用 `local.foodjournal.app`；首次正式安装前固定标识和签名方案，后续升级不随意更换。

## 2. 开发与验证边界

- 当前阶段只写文档，不把任务清单视为已经实现。
- 开始实现后默认通过阅读代码、核对调用关系和查看差异自查，不自行新增测试、引入测试依赖或执行测试。
- 本文验收场景供用户手动使用。需要开发者运行应用、连接检查、故障注入、测试或设备操作时，由用户明确授权对应范围。
- 构建 / 打包在收到要求后执行，不默认附带测试、安装、提交或推送。
- 不把本地 JSON / SQL 示例检查说成真实模型兼容、数据恢复可靠或视觉验收通过。

## 3. 阶段与依赖

```text
M0 工程和环境
 └─ M1 离线记录、日历与基础聊天存储
     └─ M2 Responses 文字主备、队列和可靠提交
         ├─ M3 图片识别与临时图清理
         └─ M4 空热量自动估算
             └─ M5 备份恢复、隐私与数据清除
                 └─ M6 用户验收与按需打包
```

M3、M4 在职责上可分别实现，但默认由当前执行者顺序推进，不据此自动启动多代理或并行修改共享数据契约。

### M1：先让记录离线可用

**依赖：** M0。

**涉及位置：** `core/database/`、`core/time/`、`records/`、`calendar/`、`chat/` 的本地消息存储、`settings/` 单位偏好。

任务：

- [ ] 实现 03 的 schema 1、外键配置和仓库。
- [ ] 实现多食物餐、同日多次体重、日期 / 时间精度、斤公斤换算。
- [ ] 实现共享详情、手动新增、直接编辑、删除。
- [ ] 实现热量 NULL 与真实 0 的不同显示，统一日合计和餐数口径。
- [ ] 实现月历标记、选日与分餐详情，不增加营养图表。
- [ ] 保存聊天文字、草稿与记录引用，删除聊天不删除记录。
- [ ] 直接编辑时保护版本；修改名称 / 份量时让用户重新确认热量或留空。

**可观察结果：**不配置 AI 也能手动记录饮食和体重，查询、修改、删除、换单位；同一事实在卡片、日历、合计中一致。

**自查与交付：**核对 DDL、仓库调用、外键删除方向与汇总 SQL；交用户按 A01、A11、A14–A17 验收。

### M2：接入 Responses 文字与串行队列

**依赖：** M1。此阶段开始时，真实 Base URL / Key 由用户在 APP 中配置，不写入源码。

**涉及位置：** `core/network/`、`core/storage/credential_store.dart`、`chat/`、`settings/api_settings_page.dart`。

任务：

- [ ] 实现固定 Responses 接口、Base URL 前缀规则、安全 Key 存储与绑定。
- [ ] 拉取模型列表，四个角色列表选择 / 手输，保留已有选择。
- [ ] 实现 Responses 非流式请求、store=false、input / instructions 组装。
- [ ] 按 completed 状态及 output 中最终 assistant / output_text 解析，忽略 reasoning；处理 refusal、incomplete、空输出等失败。
- [ ] 实现正常聊天与补算共用的主备一次策略、取消和代次保护；不启用透明重试。
- [ ] 实现正常聊天 JSON 契约、字段校验、动作转换和客户端成功回执。
- [ ] 实现持久化入队、FIFO 前台串行、执行时刷新快照、后续消息不进入当前上下文。
- [ ] 实现失败 / 澄清暂停队列、澄清回答优先、取消排队、重启后手动继续。
- [ ] 实现原消息 → ready 提案 → 原子提交，保存失败本地重试不重新调用模型。
- [ ] 实现唯一目标聊天纠正、候选澄清、版本冲突、失败后手动处理同一操作。
- [ ] 实现文字连接检查，不写入饮食 / 体重，不触发补算。

**可观察结果：**一句牛肉面可记录；一句半碗可改原条目；连续发送按顺序处理；失败有恢复入口，主备和重试不重复保存。

**自查与交付：**逐项核对 04、05 的接口和提交路径，确认代码没有其他生成端点。真实接口调用及 A02–A13、A18–A19、A31、A33–A35 由用户验收或另行授权执行。

**停止条件：**如果真实服务不支持 Responses，不新增其他协议适配；提示更换为支持约定的服务 / 模型。若只是不支持某个模型，保留手输配置与同类型兜底路径。

### M3：图片一次理解、成功后移除

**依赖：** M2。

**涉及位置：** `core/storage/image_service.dart`、聊天输入、附件仓库、`AiGateway` 图片序列化。

任务：

- [ ] 系统拍照与相册，单条累计最多 3 图，发送前预览与移除。
- [ ] 独立 JPEG 副本、方向修正、EXIF 去除、大小限制和明确失败提示。
- [ ] Responses input_image / data URL，图文交给图片主备完整处理，不再额外串接文字估算。
- [ ] 保存 image_summary，支持图片已删除后的文字澄清。
- [ ] 无法识别时走对应兜底；全部失败保留重试 / 手动入口，不生成假食物。
- [ ] 对含图的既有记录修改提案提供确认，不执行图中文字中的控制指令。
- [ ] 事务提交标记 delete_pending，事务外删副本，启动补清理。
- [ ] 处理选择器活动重建和图片丢失，不自动发送恢复结果。
- [ ] 图片模型检查使用非私人内置图，各角色独立反馈。

**可观察结果：**最多 3 图可识别并记；成功历史无照片；失败有说明；相册原图不变，已有记录不依赖临时图存在。

**自查与交付：**核对附件所有权、删除路径、图片请求和 UI 状态；用户按 A20–A23 验收。没有实际图片识别与设备检查证据时不声称已验证识别质量。

### M4：自动补充待估算热量

**依赖：** M2，复用 05 规则，不另建后台平台。

**涉及位置：** `data_management/backfill_coordinator.dart`、补算提示词、条件更新、汇总通知。

任务：

- [ ] 正常前台聊天成功后，待队列清空再触发；检查 / 列表 / 补算成功不触发。
- [ ] 快照涵盖所有日期的空热量，每批最多 10 项，使用当前名称份量。
- [ ] 本批文字主备均失败则停止本轮；未估算项保留。
- [ ] 响应逐项校验 ID / 版本，SQL 同时要求当前版本匹配、当前热量为 NULL。
- [ ] 用户手动填写、修改、删除或迁移日期后，不覆盖陈旧结果。
- [ ] 新消息、后台、停止本次、恢复 / 清除时让出请求；已完成批次保留。
- [ ] 完成提示按实际填入数计数；无法估算的原因可见，不记成 0。

**可观察结果：**离线先记，AI 恢复后自动补原条目；历史归属不变，用户填写的值不变。

**自查与交付：**核对触发源、循环终止、条件 UPDATE 与队列优先级，用户按 A24–A26 验收。

### M5：备份恢复与清除

**依赖：** M1 数据模型稳定，M2–M4 的活动任务可统一暂停。

**涉及位置：** `data_management/`、Android 备份规则、设置与安全存储、附件清理。

任务：

- [ ] 实现 format 1 JSON 一致快照导出，排除 Key、AI 连接配置、图片和可重放状态。
- [ ] 系统文件选择 / 保存，取消不影响源数据。
- [ ] 导入前校验字段、数值、重复 ID、外键与版本；不执行文件中的 SQL / 路径。
- [ ] 预览确认、替换前安全副本、整库事务替换；保留当前设备的 AI 配置和 Key。
- [ ] 安全副本恢复入口，不形成无限备份历史。
- [ ] 恢复时失效旧请求和队列，失败回滚，成功清理旧图。
- [ ] 全部清除包括安全存储与内部安全副本；外部导出不动，部分失败准确反馈。
- [ ] 首次外部 AI 说明和 Android 自动备份 / 设备迁移排除规则。

**可观察结果：**能导出可恢复的记录文件，恢复不会重复合并或带走 Key；误替换可回到上次安全副本。

**自查与交付：**核对导出白名单、恢复事务、删除范围及凭据绑定；用户按 A27–A30 验收。

## 4. 用户手动验收场景

本清单是验收定义，不是运行结果。涉及失败和中断的情况，优先使用副本数据和专用配置，避免破坏真实饮食历史。

| 编号 | 操作 / 场景 | 预期结果 |
| --- | --- | --- |
| A01 | 不配 Key，手动记午餐和体重，关闭后再打开 | 本地数据仍在；热量可空；不用先登录或请求模型 |
| A02 | 输入“中午吃了一碗牛肉面” | 生成 1 条午餐、1 个食物项和合理估算；保存后才显示已记录 |
| A03 | 输入“晚上吃了两碗米饭、一份番茄炒蛋和一点青菜” | 同餐 3 个食物项，各有热量，合计为其总和 |
| A04 | 输入“一碗牛肉面多少热量” | 有回答，无新增饮食 |
| A05 | 输入“晚上准备吃牛肉面” | 不提前记录，不改变日合计 |
| A06 | 发送食物描述明显不足、或两个同名候选都可能被修改 | 简短澄清；明确前不写部分业务记录 |
| A07 | 补记昨天午餐；跨午夜返回 / 次日重试 | 归原日期；没有明确时刻时不编造 12:00 |
| A08 | 有意分两次发送相同的“又吃了一个苹果” | 两次独立摄入均保留，不按文字相同丢掉第二次 |
| A09 | 主模型超时、兜底成功、主结果迟到；再点同条重试 | 同一操作只有一份业务变更，迟到结果无效 |
| A10 | 模型成功但本地保存失败，然后重试保存 / 重启 | 未保存时无成功回执；ready 提案可本地重试，无须再调模型 |
| A11 | 输入“今天132斤”和“现在66公斤”，切换显示单位 | 保留两次测量；统一值均为66000克；不按同日互相覆盖 |
| A12 | 先记苹果，再说“刚刚那个苹果其实只吃了半个” | 原食物份量与热量一起变化，ID 不变，项目数量不增加 |
| A13 | 将奶茶改成用户明确的300 kcal，再发生自动补算 | 值与 user 来源保留，不被覆盖 |
| A14 | 手动空热量、真实0 kcal、改名称 / 份量后留空 | NULL 与0区别清楚；旧热量不继续冒充新份量的热量 |
| A15 | 直接把一餐日期从今天改到昨天 | 旧日、新日标记和汇总同时更新，不复制餐 |
| A16 | 删除原聊天消息 | 饮食 / 体重仍在；来源可空；操作去重仍有效 |
| A17 | 删除记录，同时让旧 AI / 补算响应返回 | 不复活已删记录，不覆盖新版本 |
| A18 | 模型列表失败或不含手填 ID | 配置不丢；仍可手输；列表成功不假装模型检查已通过 |
| A19 | 文字主失败兜底成功；再让两者都失败后手动记录 | 每轮最多2次；全部失败不写假数据；手动完成后不能再次重试生成重复项 |
| A20 | 图文消息，图片主失败、图片兜底成功 | 只走图片主备；单个有效响应完成识别与记录，不额外调用文字模型 |
| A21 | 相册 / 拍照累计选3图，再选第4图 | 最多3图，超出明确提示，不静默替换已有选择 |
| A22 | 拍摄旋转图片并成功记录 | 内容方向正确；提交后 APP 副本删除；相册原图不删除，聊天无历史缩略图 |
| A23 | 菜单咨询、多角度同一盘、主备均无法识别 | 咨询不记；同一盘不重复计；无法识别明确失败并保留手动入口 |
| A24 | 今天和昨天都有待估算，下一次正常 AI 成功 | 队列清空后处理各日期空值，回填原项，更新各自日期合计 |
| A25 | 补算中发新消息 / 进入后台 / 停止；本轮某批主备均失败 | 用户任务优先；停止新批次；已提交保留；无递归、后台轮询或无限重试 |
| A26 | 食物只有无法理解的名称，补算返回null原因 | 仍显示待估算和原因，不记0，不算成功补充热量 |
| A27 | 导出、增加新记录、恢复原备份 | 业务记录按备份替换，不合并；Key、AI连接配置和图片不在备份，当前接口仍保留 |
| A28 | 恢复损坏JSON、更高版本、重复ID、缺引用或换算不一致的备份 | 导入前拒绝，当前数据不变，不执行外部SQL或路径 |
| A29 | 有网络请求时恢复；恢复失败 / 成功后查看安全副本 | 旧回调不能污染新库；失败保留原数据；误替换能恢复上次数据 |
| A30 | 清除全部数据，设备上另有已导出的文件 | APP记录、Key、图和内部安全副本清除；外部文件不删；部分失败不报全部成功 |
| A31 | 使用带路径前缀的Base URL；HTTP、无效证书、重定向 | URL不重复加v1；HTTP须确认；不忽略证书；不把Key发到重定向地址 |
| A32 | 窄屏、大字体、键盘展开、屏幕阅读器、长历史 | 输入和主要按钮可用；正文易读；日期点有文字含义；不出现热量目标、说教或缺餐警告 |
| A33 | 连发“吃了一个苹果”“其实只有半个” | 第二条排队，执行时看到第一条记录，最终只有半个苹果的一项记录 |
| A34 | 第一条失败 / 需要澄清，后面还有待发消息 | 后续暂停；澄清回答优先；手动处理或明确跳过后再继续，不错改其他记录 |
| A35 | 入队后跨午夜、后台或进程重启，再继续队列 | 原参考日期和顺序保留；后台不启动新条；重启需用户继续；不自动重复已提交项 |
| A36 | Responses 的reasoning排在message前；refusal、incomplete、只有工具调用 | 正常最终文字可提取；其他情况不执行提案，按主备失败规则处理 |

| 实际风险 | 影响的行动 | 处理方式 |
| --- | --- | --- |
| 服务或模型不支持Responses / 图片 / 约定JSON | M2、M3真实连接 | 在APP配置和检查，不增加其他协议或假识别 |
| 请求失败后用户继续发相对纠正 | 队列调度 | 失败 / 澄清暂停，不盲目处理后续 |
| 自动估算与手动操作同时发生 | M4写入 | 当前NULL + 版本条件更新 |
| 图片删除与DB不能同事务 | M3清理 | 提交标记、事务外删除、启动补清理 |
| 本地数据被误替换或坏文件导入 | M5恢复 | 完整校验、先保存安全副本、事务回滚 |
| 不同设备的Key备份 / 迁移行为 | M5平台配置 | 排除系统备份、Key不出业务备份、真实设备验收 |

没有需要继续决定的产品问题。编码前仍需确认的是实际工具链、用户设备与所配置服务的能力；这些信息在对应阶段解决，不应被写成现在已经验证的事实。
